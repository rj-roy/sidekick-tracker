I went through under `sidekick-server/src`, focused on `modules/auth`, `modules/session`, `middleware/`, `utils/`, `config/env.ts`, and `app.ts`. The auth system is already quite mature (PKCE + nonce + state, `timingSafeEqual` comparisons, hashed session tokens, session rotation with grace window, encrypted Google tokens, HMAC CSRF tokens, security event logging, TTL cleanup). The gaps that remain are specific, real ones I found by reading the code:

**1. CORS allowlist doesn't include the extension origin (`app.ts`)**
```js
app.use(cors({ origin: env.appOrigins, credentials: true }));
```
`env.appExtensions` (the `chrome-extension://<id>` origins) is defined in `config/env.ts` and is used by `csrf.middleware.ts`'s `isTrustedOrigin()`, but it's never passed into `cors()`. Only `appOrigins` is. So the CSRF layer trusts the extension, but the CORS layer — which runs first — doesn't allow it. Fix: build the `origin` option as a function that checks both `appOrigins` and `appExtensions` (mirror `isTrustedOrigin`).

**2. Rate limiting is in-memory only (`middleware/rate-limit.middleware.ts`)**
`createRateLimit` wraps `express-rate-limit` with no `store` option, so it defaults to `MemoryStore`. On `/auth/google/login`, `/auth/google/callback`, etc., this only protects a single process — with more than one server instance (or a restart) the limits reset/don't share state. Needs a shared store (Redis) if this runs behind a load balancer, or the brute-force/enumeration protection on the OAuth endpoints is effectively per-instance.

**3. `revokeOnHighRiskAnomaly` defaults to `false` (`config/env.ts` / `session.service.ts`)**
`detectAnomaly()` in `SessionService` correctly flags `SESSION_HIGH_RISK_ANOMALY` when both IP and user-agent family change on a request, but actual revocation only happens if `REVOKE_ON_HIGH_RISK_ANOMALY=true` is set — and the default is `false`. As shipped, a stolen session token used from a different device+network is only logged, not cut off automatically.

**4. No automated response to repeated OAuth failures**
`OAUTH_STATE_MISMATCH` / `OAUTH_LOGIN_FAILURE` events are logged via `logSecurityEvent`, but nothing consumes that stream — no escalating lockout, alerting hook, or IP ban beyond the flat rate limit on `/google/login` and `/google/callback`.

**5. Session token is dual-purpose between cookie and Bearer, with no distinct credential for the extension**
`middleware/auth.middleware.ts`'s `extractToken()` accepts the same raw session token either from the httpOnly cookie or an `Authorization: Bearer` header. Looking at the extension side (`background/index.ts`), it literally reads the httpOnly cookie via `chrome.cookies.get(...)` and re-sends the same secret as a Bearer token from `chrome.storage.session`. The server treats both as identical, full-privilege credentials with the same TTL/rotation rules — there's no separate, narrower-scoped or shorter-lived token type for the extension client, so the httpOnly protection is effectively bypassed by design rather than by a bug, and the server has no way to distinguish/limit extension-origin sessions from browser-cookie sessions.

**6. No explicit security headers beyond `helmet()` defaults**
`app.ts` calls `app.use(helmet())` with no configuration — no explicit `Cross-Origin-Resource-Policy`, `Permissions-Policy`, or a tightened CSP for the JSON API. Not critical for a pure API, but worth locking down explicitly rather than relying on defaults.
