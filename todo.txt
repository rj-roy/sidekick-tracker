## 1. 🔴 Require the OAuth nonce — this is still not fully enforced

You correctly generate a nonce:

```ts
const nonce = generateNonce();
```

and send it to Google:

```ts
nonce: options.nonce,
```

You also store it:

```ts
JSON.stringify({ v: codeVerifier, n: nonce })
```

And your JWT verifier supports nonce verification:

```ts
if (expectedNonce && claims.nonce !== expectedNonce) {
    throw ...
}
```

### But here's the problem

In the callback:

```ts
let nonce: string | undefined;
```

If the cookie is malformed or doesn't contain `n`, you eventually do:

```ts
AuthService.getCallbackCred(code, verifier, nonce ?? "");
```

Then:

```ts
verifyGoogleIdToken(tokens.id_token, nonce);
```

Because `nonce` becomes `""`, this condition:

```ts
if (expectedNonce && claims.nonce !== expectedNonce)
```

doesn't execute.

So you have:

```text
nonce cookie missing
       ↓
nonce = ""
       ↓
verifyGoogleIdToken(..., "")
       ↓
nonce NOT checked
```

### Fix

Make nonce mandatory:

```ts
if (!nonce) {
    throw new ApiError(
        400,
        "OAuth authentication failed",
        "OAUTH_ERROR"
    );
}
```

before calling `getCallbackCred()`.

And preferably make the service signature:

```ts
getCallbackCred(
    code: string,
    codeVerifier: string,
    nonce: string
)
```

instead of allowing an optional nonce.

**Severity: Medium**

This is the most important remaining OAuth issue.

# 2. 🔴 Your `upsertByEmail()` can potentially re-bind an existing account

This is the other thing I would change.

You have:

```ts
upsertByEmail(userData)
```

which does:

```ts
$set: {
    googleId: userData.googleId,
    ...
}
```

So an existing user:

```text
User
googleId = GOOGLE_A
email = user@example.com
```

could potentially become:

```text
googleId = GOOGLE_B
```

if the email-based fallback is reached.

Your normal Google login path already has a verified Google `sub`, so **you don't actually need to silently replace an existing Google identity based on email**.

### Safer rule

If email exists:

```text
email exists
      ↓
does googleId match?
   /        \
 yes         no
 ↓           ↓
login       reject / explicit account-linking flow
```

Don't do:

```text
email matches
     ↓
replace googleId
```

I'd remove the automatic `upsertByEmail()` identity takeover behavior.

This is especially important if you ever add another authentication provider.

**Severity: Medium–High depending on account history/provider design**

# 3. 🟠 Bearer session token is now your biggest client-side concern

I checked the extension too.

The extension does this:

```ts
const token = stored[SESSION_STORAGE_KEY];

Authorization: `Bearer ${token}`
```

And the background service worker copies the server's session cookie:

```ts
chrome.cookies.get(...)
```

into:

```ts
chrome.storage.session
```

This means the raw authentication token exists outside the HttpOnly cookie.

That's intentional for your extension architecture, but it means:

```text
HttpOnly protection
       ↓
doesn't protect the copied extension token
```

The good news is that you're using:

```ts
chrome.storage.session
```

rather than ordinary web `localStorage`, which is much better.

### I would keep this architecture if the extension needs it.

But make sure:

* content scripts cannot directly access the session token
* arbitrary extension messages cannot request the token
* only trusted extension contexts use it
* never put it in page-accessible storage
* never expose it through DOM/window globals

From the code I checked, I **don't see the token being deliberately exposed to the Gmail page**, which is good.

# One subtle issue I'd improve

Your session rotation creates the replacement **before** atomically claiming the old session:

```text
create new session
      ↓
claim old session
```

You correctly clean up the replacement if claiming fails, so it's not a security hole.

But architecturally I'd prefer the rotation operation to be more tightly controlled, because a crash between:

```text
insert new session
```

and:

```text
claim old session
```

can leave an orphan session in MongoDB.

Your cleanup/TTL will eventually handle it, so this isn't a major concern.
