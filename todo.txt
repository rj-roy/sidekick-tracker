# Remaining issues I would still fix

## 1. ⚠️ Old rotated session can still authenticate during grace period

This code:

```ts
if (session.rotatedToHash) {
    const graceMs = env.session.rotationGraceSeconds * 1000;

    if (Date.now() - rotatedAt > graceMs) {
        throw new ApiError(...);
    }

    return { session };
}
```

During the grace period, the **old token remains valid**.

That means if an attacker steals the old token, they can continue making authenticated requests for up to:

```text
SESSION_ROTATION_GRACE_SECONDS
```

Your default is 10 minutes.

### Why this is the main remaining security concern

Imagine:

```text
12:00 attacker steals old token
12:01 legitimate user triggers rotation
12:01 old token marked rotated
12:01–12:11 attacker can still authenticate
```

Also, the old token doesn't receive the replacement token because the server only stores:

```ts
rotatedToHash
```

—not the raw replacement token, which is correct because you should never store it.

### My recommendation

For a normal browser cookie session, **you probably don't need a 10-minute grace period**.

Use something much shorter, such as:

```text
0–30 seconds
```

If the grace period exists specifically for concurrent requests, even:

```text
5–15 seconds
```

may be enough.

**Severity: Medium**

---

## 2. ⚠️ Session expiration is checked after `rotatedToHash`

Your order is:

```ts
if (session.rotatedToHash) {
   ...
   return { session };
}

if (session.expiresAt.getTime() <= Date.now()) {
   ...
}
```

So a rotated session that is already expired could theoretically enter the grace-period branch first.

It should be:

```ts
if (session.expiresAt.getTime() <= Date.now()) {
    throw ...
}

if (session.rotatedToHash) {
    ...
}
```

The secure validation order should generally be:

```text
1. token format
2. session exists
3. revoked?
4. expired?
5. rotated?
6. anomaly detection
7. touch / rotate
```

This is a **small but real logic bug**.

**Severity: Low–Medium**

---

## 3. ⚠️ `state` comparison should ideally be timing-safe

You have:

```ts
savedState !== state
```

For OAuth state, this is not a major practical vulnerability because the value is random and server-side cookie protected.

Still, for consistency:

```ts
crypto.timingSafeEqual(...)
```

would be better.

More importantly, validate both values are expected lengths before comparison.

**Severity: Low**

---

## 4. ⚠️ OAuth cookies aren't cleared on failed authentication

You clear them only after successful login:

```ts
res.clearCookie(env.cookies.oauthState, ...)
res.clearCookie(env.cookies.oauthVerifier, ...)
```

If this happens:

```text
state mismatch
Google rejects code
invalid ID token
PKCE exchange failure
```

the OAuth cookies remain until expiration.

They're short-lived, so this isn't a serious vulnerability, but better behavior is to clear them whenever the callback completes, including failures.

For example, ensure cleanup using `finally` around the callback process.

**Severity: Low**

---

## 5. ⚠️ Your server starts listening before MongoDB is confirmed connected

Currently:

```ts
server = app.listen(port, async () => {
    try {
        await connectDB();
        await initializeIndexes();
        startJobs();
    }
});
```

This means the server can accept requests before:

```text
MongoDB connected
indexes initialized
```

For authentication, I would reverse it:

```text
connect DB
    ↓
initialize indexes
    ↓
start server
```

Otherwise, under deployment/startup conditions, requests could reach auth endpoints before the database is ready.

**Severity: Medium operational/security reliability**

---

## 6. ⚠️ `SESSION_SECRET` length is checked, but entropy isn't

You require:

```ts
if (sessionSecret.length < 32)
```

Good, but this accepts:

```text
aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
```

which is 32 characters but terrible cryptographically.

For a production secret, generate something like:

```text
randomBytes(32).toString("base64")
```

You don't necessarily need to implement entropy detection in code, but ensure the deployment secret is genuinely random.

Same principle for other secrets.

**Severity: Configuration-dependent**

---

## 7. ⚠️ IP/User-Agent changes are only logged, not acted on

You do:

```ts
detectAnomaly(session, rotate);
```

and log:

```text
SESSION_IP_CHANGED
SESSION_UA_CHANGED
```

That's good for detection.

But a stolen session token from a completely different:

```text
IP + User-Agent
```

still works.

I **would not automatically revoke on IP change**, because mobile users, VPNs, proxies, etc. change IPs.

But you could add risk rules:

```text
IP changed + radically different UA
        ↓
log high-risk event
        ↓
optionally revoke / require reauthentication
```

Not mandatory for your current application.

**Severity: Enhancement**

# One important thing: your Bearer token support changes your threat model

You accept:

```text
Authorization: Bearer <session token>
```

and also:

```text
HttpOnly Cookie
```

This means your session token isn't purely protected by `HttpOnly` cookies, because somewhere a client may possess the raw token to send it as a Bearer token.

If Sidekick's Chrome extension needs Bearer authentication, that's understandable.

But then **do not store the raw session token in ordinary extension `localStorage`**.

If your architecture allows it, prefer:

```text
Web app → HttpOnly cookie
Chrome extension → carefully managed token storage
```

or separate authentication/session mechanisms for browser extension and web clients.

The server-side implementation itself is okay—the important question is **where the client stores the Bearer token**.
